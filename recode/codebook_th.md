# Codebook ภาษาไทย สำหรับจัดประเภทด้วยมือ (v1.1)

**กติกาสำคัญ**
- จัดประเภทจากข้อความของ advisory ใน `items.md` เท่านั้น ห้ามค้นข้อมูลเพิ่ม ห้ามเดาเกินข้อความ ถ้าข้อมูลไม่พอให้ใส่ `UNCLEAR`
- **ห้ามเปิด `_key_do_not_open.json`** และห้ามดูผลของ Claude หรือ Codex ก่อนกรอกเสร็จ ไม่อย่างนั้นค่า kappa จะใช้ไม่ได้
- กรอกลง `answers.csv` ใช้ค่าตามที่กำหนดไว้ข้างล่างเป๊ะ ๆ (ตัวพิมพ์ใหญ่ทั้งหมด) ถ้า `relevant` = N ให้เว้นช่องอื่นว่าง
- ใช้เวลาประมาณ 2–4 นาทีต่อรายการ ถ้าไม่แน่ใจ ให้เลือกคำตอบที่ใกล้ที่สุดแล้วจดเหตุผลไว้ในช่อง `note`

## 1. `relevant` (Y / N): เป็นบั๊กการถอนสิทธิ์หรือไม่

ตอบ **Y** เมื่อครบทั้ง 2 ข้อ
1. **ผู้ใช้ (หรือ token, อุปกรณ์) เคยมีสิทธิ์จริง แล้วสิทธิ์นั้นถูกถอน** เช่น ถูกลดบทบาทหรือลดสิทธิ์, ถูกถอดออกจากทีม กลุ่ม โปรเจกต์ หรือ org, บัญชีถูกปิด ลบ ล็อก หรือแบน, token/API key/share link/invitation ถูกเพิกถอนหรือลบ, logout, เปลี่ยนรหัสผ่าน, repo เปลี่ยนจาก public เป็น private
2. **หลังถอนสิทธิ์แล้ว ยังใช้สิทธิ์นั้นได้อยู่อย่างน้อยบางส่วน**

**ตอบ N เช่น**
- การตรวจเพิกถอนใบรับรองของ TLS/X.509 (CRL, OCSP), SSH CA key, PGP, verifiable credential
- คนที่ **ไม่เคยมีสิทธิ์มาก่อน** เข้าถึงได้ เช่น IDOR หรือไม่มีการตรวจสิทธิ์ตั้งแต่แรก
- API สำหรับเพิกถอนที่ใครก็เรียกได้ (เช่น เพิกถอน token ของคนอื่นได้)
- session หรือ token ที่หมดอายุตามเวลาแล้วยังใช้ได้ (timeout ไม่นับว่าเป็นการถอนสิทธิ์)
- token ใช้ครั้งเดียว (เช่น reset link) ที่ใช้ซ้ำได้ เพราะไม่ใช่การถอนสิทธิ์
- คำแนะนำให้ "revoke your tokens" หลังข้อมูลรั่ว หรือ advisory ที่ withdrawn/duplicate
- หน้าเว็บยังดูได้จาก browser cache หรือปุ่ม back หลัง logout (ไม่ได้ใช้สิทธิ์กับ server)

**กฎ R1:** การที่ยังอ่านข้อมูลที่ตัวเองไม่มีสิทธิ์เห็นแล้วได้ **นับว่าใช้สิทธิ์ที่ถูกถอน** แม้จะเป็นแค่ชื่อเรื่องหรือ metadata ที่รั่วผ่าน notification เก่า, star หรือ watch

## 2. `carrier`: สิทธิ์ที่ค้างอยู่เก็บอยู่ที่ไหน (ตอบเฉพาะเมื่อ Y)

| ค่า | ความหมาย |
|---|---|
| `SESSION` | login session หรือ cookie ที่สร้างไว้ **ก่อน** ถอนสิทธิ์ ยังพาสิทธิ์เดิมอยู่ |
| `TOKEN` | credential ที่ออกไว้ก่อนถอนสิทธิ์ยังใช้ได้ (JWT, OAuth access/refresh token, API key, signed URL, remember-me, share link) |
| `CACHE` | cache ฝั่ง server ที่เก็บสิทธิ์หรือผลการตรวจสิทธิ์ไว้ แล้วไม่ถูกล้าง |
| `CONNECTION` | การเชื่อมต่อที่เปิดค้างไว้ก่อนถอนสิทธิ์ (WebSocket, SSE, stream, SFTP) ยังทำงานต่อ |
| `DATA` | สิทธิ์ค้างอยู่ในข้อมูลที่เก็บถาวร เช่น grant ลูก, ACL entry, group link ที่ไม่ถูกลบ หรือวัตถุที่สร้างไว้ก่อนถอนสิทธิ์ |
| `CHECK` | โค้ดไม่ได้ตรวจสถานะที่ถูกถอนเลย เช่น ไม่เช็ก flag disabled ใน endpoint บางตัว |
| `ASYNC` | งานที่ตั้งเวลาหรือเข้าคิวไว้ก่อนถอนสิทธิ์ยังรันต่อ (job, webhook, cron) |
| `UNCLEAR` | ข้อความไม่พอจะตัดสิน |

## 3. `fresh_state_detects`: การทดสอบที่เริ่มจากสถานะใหม่จะเห็นบั๊กนี้ไหม (ตอบเฉพาะเมื่อ Y)

นึกถึงการทดสอบที่ **เริ่มหลังถอนสิทธิ์แล้ว** ใช้ login ใหม่หรือ credential ใหม่ และ cache ว่าง

| ค่า | ใช้เมื่อ |
|---|---|
| `Y` | จะเห็นบั๊ก (ปกติคือ `CHECK` และ `DATA` แบบที่ login ใหม่ก็ยังเข้าได้) |
| `N` | จะไม่เห็น เพราะบั๊กต้องอาศัยสิ่งที่เกิดก่อนถอนสิทธิ์ (ปกติคือ `SESSION`, `TOKEN`, `CONNECTION`, `ASYNC`) |
| `DEPENDS` | ขึ้นกับว่า cache แยกต่อ session หรือใช้ร่วมกัน (ปกติคือ `CACHE`) หรือข้อความไม่ชัด |

**กฎ R2:** ถ้าบั๊กต้องอาศัย **วัตถุที่ผู้ใช้สร้างไว้ก่อนถอนสิทธิ์** (notification, stopwatch, watch, fork, record เก่า, share link) ให้ตอบ `N` แม้ carrier จะเป็น `DATA` เพราะการทดสอบที่เริ่มหลังถอนสิทธิ์จะไม่มีวัตถุนั้นอยู่

ถ้าข้อความบอกไว้เป็นอย่างอื่น ให้ตามข้อความ ไม่ต้องยึดค่าปกติที่ระบุไว้ในวงเล็บ

---

## 4. `revocation_kind`: อะไรถูกถอน (ตอบเฉพาะเมื่อ Y)

`PERMISSION` (ลดบทบาทหรือสิทธิ์) · `MEMBERSHIP` (ถูกถอดออกจากทีม กลุ่ม โปรเจกต์ หรือ org) · `ACCOUNT` (บัญชีถูกปิด ลบ ล็อก หรือแบน) · `CREDENTIAL` (token, key หรือ share link ถูกเพิกถอนหรือลบ) · `LOGOUT_PWCHANGE` (logout หรือเปลี่ยนรหัสผ่าน) · `OTHER` (เช่น repo เปลี่ยนเป็น private, ปิดฟีเจอร์)

---

## 5. `webapp` (Y / N): เป็นเว็บแอปหรือเว็บ API server หรือไม่ (ตอบเฉพาะเมื่อ Y)

ตอบ `Y` ถ้าเป็นแอปหรือ server ที่ให้บริการผ่านเว็บ (เช่น Gitea, Keycloak, Mattermost) ตอบ `N` ถ้าเป็น library หรือ framework (เช่น Spring Security, Symfony, library JWT), CLI หรือ protocol library
